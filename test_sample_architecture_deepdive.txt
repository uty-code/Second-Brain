# 대규모 트래픽 이커머스 백엔드 아키텍처 전면 개편 및 고가용성 장애 극복기

## 1. 개요 및 비즈니스 배경
글로벌 커머스 플랫폼 AIMS의 일간 결제 트래픽이 10배 이상 폭증하면서, 기존 단일 모놀리식 구조의 백엔드 시스템은 심각한 성능 병목과 데이터 정합성 깨짐 문제에 직면했습니다.
특히 블랙프라이데이 및 대규모 타임세일 이벤트 동안 초당 50,000건 이상의 동시 주문 요청이 인입될 때, 전통적인 RDBMS 행 레벨 락(Row-level Lock)과 외부 PG 결제 호출 간의 블로킹으로 인해 톰캣(Tomcat) 스레드 풀이 고갈되고 연쇄적인 서비스 장애가 발생했습니다.

우리는 이 문제를 근본적으로 해결하기 위해 2026년 상반기 동안 다음과 같은 4대 핵심 아키텍처 혁신을 단행했습니다:
1. Java 21 가상 스레드(Virtual Threads) 도입을 통한 동시 I/O 처리 극대화
2. Redis(Redisson) 기반 분산 락을 활용한 초당 재고 차감 상호 배제 보장
3. 트랜잭셔널 아웃박스(Transactional Outbox) 패턴과 Apache Kafka를 통한 무손실 비동기 이벤트 스트리밍
4. CQRS 패턴 및 Neo4j 지식 그래프를 이용한 실시간 추천 및 연관 데이터 서빙

---

## 2. 동시성 모델 전환: Java 17 스레드 풀에서 Java 21 가상 스레드로
과거 2024년까지 당사 백엔드는 Java 17 LTS 환경에서 ThreadPoolExecutor 기반(Core 100, Max 400)의 플랫폼 스레드 모델을 운영했습니다.
하지만 외부 결제 API, 배송사 연동 등 블로킹 I/O 작업이 3초 이상 지연될 경우 전체 작업 큐가 가득 차고 타임아웃 예외가 연쇄 폭발했습니다.

우리는 2026년 3월 Java 21 가상 스레드(Project Loom)로 전면 마이그레이션을 완료했습니다.
가상 스레드는 OS 스레드에 1:1 매핑되지 않고, 소수의 캐리어(Carrier) 스레드 위에서 수만 개의 가상 스레드가 사용자 영역에서 스케줄링됩니다.
소켓 읽기/쓰기나 DB 호출로 인해 I/O 블로킹이 발생하면 캐리어 스레드는 즉시 해당 가상 스레드를 언마운트(unmount)하고 다른 유휴 가상 스레드를 실행합니다.
이를 통해 메모리 오버헤드를 기존 스레드당 1MB에서 수 KB 수준으로 낮추었으며, 동일 서버 스펙에서 동시 연결 처리량을 450% 향상시켰습니다.

주의점 및 피닝(Pinning) 방어:
가상 스레드 내부에서 synchronized 블록을 호출하면 캐리어 스레드가 블록에 묶여 다른 작업을 처리하지 못하는 스레드 피닝(Thread Pinning) 현상이 발생합니다.
우리는 코드베이스 전반의 동기화 구문을 java.util.concurrent.locks.ReentrantLock으로 전면 교체하여 피닝을 원천 차단했습니다.

## 3. 재고 정합성 사수: Redis 분산 락(Distributed Lock)과 Redisson
선착순 1,000개 한정 수량 상품에 10만 명의 사용자가 동시에 구매 버튼을 클릭할 때, DB의 'SELECT FOR UPDATE'는 심각한 DB 커넥션 풀 고갈을 초래합니다.
우리는 인메모리 NoSQL인 Redis와 Redisson 클라이언트를 도입하여 임계 영역(Critical Section)의 진입을 통제했습니다.

핵심 설계 및 락 획득/해제 흐름:
1. 스핀락(Spin Lock) 대신 Redis Pub/Sub을 사용하는 Redisson의 RLock 인터페이스를 채택하여 Redis CPU 부하를 방지했습니다.
2. 락 획득 시 tryLock(waitTime, leaseTime)을 설정하여, 5초 동안 락을 얻지 못하면 빠르게 Fallback(대기열 진입 또는 품절 안내)을 수행하도록 했습니다.
3. 비즈니스 로직이 네트워크 지연으로 길어질 때 락이 조기 해제되지 않도록 Redisson의 와치독(Watchdog) 백그라운드 태스크가 30초 주기로 TTL(Time-to-Live)을 자동 갱신합니다.

가장 치명적이었던 '트랜잭션 커밋 이전 락 해제' 버그 해결:
초기 구현 시 스프링 @Transactional 메서드 내부에서 락을 해제하도록 작성하여 장애가 발생했습니다.
락이 풀린 찰나에 DB 트랜잭션이 아직 커밋되지 않은 상태에서 다른 스레드가 락을 획득하고 과거 재고 데이터를 읽어 중복 판매(Overselling)가 발생한 것입니다.
이를 해결하기 위해 TransactionSynchronizationManager를 활용하여 DB 트랜잭션이 완벽히 commit()된 직후에만 Redis 락을 반납하는 AOP 구조를 확립했습니다.

## 4. 이중 쓰기(Dual-Write) 불일치 해결: 트랜잭셔널 아웃박스 패턴
주문 서비스에서 결제가 완료되면 원장 RDBMS(MSSQL)에 주문 상태를 'PAID'로 변경하고, 물류 및 알림 서비스를 위해 Apache Kafka에 'OrderPaid' 토픽 이벤트를 발행해야 합니다.
그러나 네트워크 단절이나 카프카 브로커 장애가 발생할 경우:
- DB 커밋은 성공했으나 카프카 이벤트 발행은 실패하거나,
- 카프카 이벤트는 발행되었으나 DB 커밋 롤백이 발생하는 '이중 쓰기 불일치(Dual-Write Inconsistency)' 위험이 상존했습니다.

우리는 2단계 커밋(2PC)의 블로킹 단점을 배제하고 최종 일관성(Eventual Consistency)을 달성하기 위해 '트랜잭셔널 아웃박스 패턴(Transactional Outbox Pattern)'을 도입했습니다:
1. 로컬 트랜잭션 단일 묶음:
   주문 테이블(orders) 갱신과 아웃박스 테이블(outbox_events)에 이벤트 페이로드를 INSERT하는 작업을 단일 DB 트랜잭션으로 커밋합니다.
2. 메시지 릴레이(Message Relay):
   별도의 폴링 퍼블리셔(Polling Publisher) 또는 CDC(Debezium) 엔진이 아웃박스 테이블을 주기적으로 읽어 Kafka 브로커로 안전하게 전송합니다.
3. 멱등성 컨슈머(Idempotent Consumer):
   Kafka의 At-least-once 전송 특성으로 인한 중복 수신을 방지하기 위해 컨슈머 측에 고유 이벤트 ID 기반의 멱등 처리 필터를 구축했습니다.

## 5. 지식 그래프 및 연관 데이터 분석: Neo4j
주문 데이터와 고객 리뷰, 상품 메타데이터가 쌓이면서 복잡한 다대다(N:M) 관계 탐색의 필요성이 커졌습니다.
기존 관계형 DB에서 5단계 이상의 JOIN을 수행할 때 쿼리 속도가 수 초 이상 지연되었습니다.
우리는 Neo4j 그래프 데이터베이스를 도입하여 고객(Customer), 상품(Product), 카테고리(Category), 이벤트(Event)를 노드로 모델링하고 이들 간의 관계를 엣지(Edge)로 정의했습니다.
Cypher 쿼리를 통해 인덱스 프리 인접성(Index-free Adjacency)을 활용함으로써 수 밀리초 만에 5-hop 이상의 복합 연관 상품 그래프를 탐색할 수 있게 되었습니다.

## 6. 결론 및 성과
이번 아키텍처 개편을 통해 AIMS 플랫폼은 다음과 같은 괄목할 성과를 거두었습니다:
- 주문 처리 지연 시간(P99 Latency): 2,800ms -> 180ms로 93% 단축
- 이벤트 타임세일 중 동시 주문 결제 정합성 오류: 0건 (Overselling Zero 달성)
- 서버 인프라 비용: 동시성 효율 극대화로 컨테이너 파드 수를 40% 감축

이러한 지식 컴파일러와 고가용성 분산 아키텍처는 향후 글로벌 멀티 리전(Multi-Region) 확장 시 핵심 기반 기술로 작동할 것입니다.
