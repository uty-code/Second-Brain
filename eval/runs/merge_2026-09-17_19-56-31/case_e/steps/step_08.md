## 정의
Redis 분산 락은 다중 서버 환경에서 공유 자원에 대한 상호 배제(Mutual Exclusion)를 보장하기 위해 인메모리 키-값 저장소를 락 관리자로 활용하는 동시성 제어 기법입니다.

## 핵심 구성 요소
- **SETNX 원자적 명령**: 키가 존재하지 않을 때만 값을 설정하여 락 선점 여부를 단일 연산으로 결정합니다.
- **만료 시간(TTL, Expiration)**: 프로세스 비정상 종료 시 데드락(Deadlock)에 빠지지 않도록 유효 기간을 설정합니다.
- **소유자 식별자(UUID)**: 락 해제 시 다른 클라이언트가 획득한 락을 실수로 삭제하지 않도록 하기 위해 소유자 식별자가 일치할 때만 삭제해야 합니다. 이 검증과 삭제는 Lua 스크립트를 통해 단일 원자적 연산으로 수행해야 합니다.
- **파라미터**: Redisson 락 획득 메서드(tryLock) 호출 시 waitTime(락 대기 최대 시간)과 leaseTime(락 자동 반납 만료 시간)을 도메인 특성에 맞게 설정해야 합니다. leaseTime을 명시하면 와치독이 동작하지 않으므로 주의가 필요합니다.

## 동작 원리
클라이언트는 고유한 토큰 값을 생성하여 `SET key token NX PX 30000` 명령을 실행합니다. 획득에 성공하면 비즈니스 로직을 수행하고 완료 후 락을 해제합니다. 락 해제 시 소유자 식별자를 확인하여 일치할 경우에만 삭제합니다. 직접 SETNX를 폴링(스핀락)하면 Redis 부하가 가중되므로, pub/sub 기반으로 락 획득 대기를 처리하는 Redisson 클라이언트를 사용하는 것이 권장됩니다. Redisson의 와치독(Watchdog) 기능은 비즈니스 로직이 예상보다 길어질 경우 백그라운드 스레드가 만료 시간(TTL)을 주기적으로 연장하여 락이 조기 해제되는 버그를 방지합니다. 기본 연장 주기는 30초입니다.

## 정합성 함정: DB 트랜잭션과 락 해제 순서
스프링 @Transactional 안에서 락을 해제하면, DB 커밋이 완료되기 전에 다른 스레드가 락을 선점하여 커밋 이전의 과거 데이터를 읽는 정합성 깨짐이 발생할 수 있습니다. 따라서 락 해제 시점은 DB 트랜잭션 커밋 완료 이후여야 합니다.

## 확장: Redlock 알고리즘의 원리
단일 Redis 인스턴스의 장애 위험을 방지하기 위해 5대 이상의 독립적인 Redis 마스터 노드에 과반수(Quorum) 획득을 시도하는 Redlock 알고리즘이 제안되었습니다. N/2 + 1개 이상의 노드에서 유효 시간 내에 락을 얻어야 성공으로 간주합니다.

## 논쟁: Redlock의 시스템 시계 편차 한계
Martin Kleppmann은 Redlock이 시스템 시계(Clock Drift) 및 긴 GC 정지(Stop-the-world)에 취약하다고 지적했습니다. 강력한 정확성이 필요한 시스템이라면 펜싱 토큰(Fencing Token)이나 ZooKeeper 같은 합의 엔진이 더 적합할 수 있습니다.

## 장점과 트레이드오프
- **장점**: 고성능 메모리 기반으로 락 획득/해제 지연 시간이 매우 짧습니다.
- **트레이드오프**: Redis 마스터 장애 시 페일오버 과정에서 락 복제가 누락될 수 있는 신뢰성 문제와, 직접 폴링 시 Redis 부하가 증가할 수 있습니다.

## 실전 적용 사례
선착순 쿠폰 발급 및 포인트 차감 등 중복 차감 방지 로직에 사용됩니다. 또한, Spring Boot에서는 비즈니스 코드 침투를 방지하기 위해 `@DistributedLock(key = "#orderId")` 커스텀 어노테이션과 AspectJ AOP를 구현하여 선언적으로 락을 획득/해제하는 방식을 널리 활용합니다.
