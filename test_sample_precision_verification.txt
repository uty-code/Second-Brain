# 분산 결제 시스템 기술 아키텍처 및 도메인 운영 정책 심층 분석

## 1. 개요
대규모 글로벌 결제 및 주문 처리 플랫폼에서는 시스템 장애 격리와 데이터 정합성을 동시에 달성해야 합니다. 본 문서는 핵심 분산 인프라 아키텍처와 함께, 독립적으로 운영되는 비즈니스 회계 및 개발 문화 정책을 복합적으로 다룹니다.

---

## 2. 분산 트랜잭션 및 비동기 파이프라인 (핵심 기술 스택)

### 2.1 Spring Boot Microservices
현대 엔터프라이즈 결제 코어는 Spring Boot Microservices 프레임워크를 기반으로 구축됩니다.
- 각 서비스는 독립적인 배포 단위와 전용 데이터베이스를 가집니다.
- 주문 서비스(Order Service)는 고객의 주문 요청을 수신하고, 결제 서비스(Payment Service)와 통신합니다.
- 대규모 I/O 부하를 견디기 위해 가상 스레드와 비동기 논블로킹 논리를 적용합니다.
- 주문 결제 완료 후 외부 이벤트 전달을 위해 후술할 Transactional Outbox Pattern을 전적으로 채택하여 사용합니다.

### 2.2 Transactional Outbox Pattern
분산 마이크로서비스 환경에서 RDBMS 상태 업데이트와 메시지 브로커 이벤트 발행 간의 '이중 쓰기 불일치(Dual-Write Inconsistency)'를 해결하기 위해 Transactional Outbox Pattern을 적용합니다.
- 주문 상태 변경 SQL과 아웃박스 테이블(Outbox Event) 삽입을 단일 로컬 데이터베이스 트랜잭션(@Transactional)으로 묶어 원자성(Atomicity)을 보장합니다.
- 별도의 릴레이 프로세스가 커밋된 아웃박스 레코드를 폴링 또는 CDC 방식으로 읽어 Kafka Event Streaming 클러스터로 신뢰성 있게 발행합니다.
- 발행 완료 후 Outbox 레코드의 상태를 PROCESSED로 갱신하여 메시지 유실(At-Least-Once Delivery)을 원천 방지합니다.

### 2.3 Kafka Event Streaming
Kafka Event Streaming은 분산 결제 시스템의 이벤트 백본(Event Backbone) 역할을 수행합니다.
- Transactional Outbox Pattern 릴레이로부터 전달받은 '주문 완료', '결제 승인' 이벤트를 토픽에 영속화합니다.
- 파티셔닝 전략을 통해 주문 ID 기준으로 순서 보장을 달성하며, 다운스트림의 재고 서비스, 배송 서비스, 정산 서비스가 각자의 속도로 이벤트를 소비합니다.
- 시스템 장애 시에도 오프셋을 기반으로 안전하게 메시지를 재처리할 수 있습니다.

### 2.4 Redisson Distributed Lock
고동시성 주문 환경에서는 한정 수량 상품에 대한 재고 차감 시 동시성 충돌(Race Condition)이 발생합니다.
- 시스템은 Redisson Distributed Lock을 사용하여 Redis 기반의 분산 임계 영역(Critical Section)을 보호합니다.
- RLock의 `tryLock` 메서드를 통해 지정된 대기 시간 동안만 락 획득을 시도하며, 스핀 락으로 인한 CPU 낭비를 차단합니다.
- 락 획득에 성공한 단일 요청만이 주문 트랜잭션을 수행하며, 실패한 요청은 즉시 품절 응답 또는 대기열 안내를 받습니다.

## 3. 독립 운영 도메인 (비즈니스 및 거버넌스)

> [참고] 다음 도메인들은 위 분산 기술 아키텍처와 함께 논의되거나 조직 내에서 관리되지만, 시스템 간의 직접적인 기술적 의존성이나 구현 관계는 존재하지 않는 완전 독립 도메인입니다.

### 3.1 Payment PG Fee Policy (결제 대행사 수수료 정책)
결제 플랫폼 비즈니스 운영팀은 각 신용카드사 및 간편결제 PG사와 체결한 Payment PG Fee Policy를 관리합니다.
- 일반 신용카드 결제 수수료율은 거래 금액의 2.3%로 책정되며, 월 거래액 10억 원 초과 시 우대 수수료 1.8%가 적용됩니다.
- PG사와의 정산 대금 입금 주기는 영업일 기준 D+3일이며, 매월 말일 정산 명세서를 수령하여 대사(Reconciliation) 작업을 진행합니다.
- 환불 발생 시에는 원거래 수수료가 일할 계산되어 환급 처리됩니다.
- 본 수수료 정책은 순수 재무 회계 규정이며, 시스템 엔지니어링이나 메시지 큐 등 하부 기술 구현체와 직접적인 기술적 결합을 갖지 않습니다.

### 3.2 Developer Ergonomics (개발자 생산성 환경)
엔지니어링 팀은 효율적인 코드 협업과 유지보수를 위해 Developer Ergonomics 가이드라인을 정의합니다.
- 모든 백엔드 및 프론트엔드 코드는 CI 파이프라인에서 Spotless Check 및 자동 포맷터를 필수로 거쳐야 합니다.
- Conventional Commits 형식(`feat:`, `fix:`, `refactor:`)을 준수하여 의미 있는 변경 이력을 유지합니다.
- 로컬 개발 환경의 온보딩 시간을 10분 이내로 단축하기 위해 컨테이너 기반 샌드박스를 제공합니다.
- 이는 조직 문화 및 코드 품질 관리를 위한 개발 원칙으로서, 개별 비즈니스 결제 로직이나 인프라와는 무관하게 독립적으로 적용됩니다.

---

## 4. 시스템 설계 고찰 (단순 언급 맥락)
소프트웨어 아키텍처를 설계할 때는 Spring Boot Microservices 및 Kafka Event Streaming 같은 핵심 인프라의 견고함뿐만 아니라, 거시적인 관점에서 Payment PG Fee Policy에 따른 비용 최적화 방안이나 팀의 Developer Ergonomics 향상 방안도 다각도로 고려될 수 있습니다. 그러나 각 영역의 관심사는 명확히 분리되어 독립성을 유지해야 합니다.
